# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# Verification policy

Do not run verification steps on your own initiative — no dev server, no build, no lint/typecheck runs, no browser checks, no tests — unless the user explicitly asks for it in that turn. Make the code change and stop there; wait for the user to request a check.

# Planning policy

Before implementing any change, first present a short plan (what will change, which files, the approach) and wait for the user to explicitly confirm it. Do not start editing code until the user has approved the plan in that turn.

# Git policy

Never run `git commit` or `git push` on your own initiative. Only do so when the user explicitly asks for a commit or push in that turn — approval for one commit/push does not carry over to later changes.

# Long-chat summary policy

After 15 user messages have accumulated in a single chat, summarize everything done so far and all information a new chat would need to continue the work (decisions made, current state, outstanding steps), then advise the user to open a new chat.

# Code quality policy

Write code like a senior developer: think through edge cases, failure modes, and invalid inputs before considering the task done, not just the happy path.

## Commands

```bash
npm install
npm run dev       # Vite dev server (service worker is NOT registered in this mode)
npm run build     # tsc -b (typecheck) + vite build (app bundle + service worker)
npm run preview   # serve the production build locally — required to test the PWA/service worker
```

There is no test suite and no lint script configured. `npm run build` is the closest thing to a
CI check (it fails on TypeScript errors).

To work on push notifications end-to-end, the Supabase CLI is needed (see README.md's "Push
notifications setup" section) — the SQL editor alone isn't enough because the Edge Function has to
be deployed and `pg_cron` scheduled.

## Architecture

**No custom backend.** The client talks directly to Supabase (Postgres + Auth), authorized by Row
Level Security (every row scoped to `auth.uid()`) rather than an API layer. The only server-side
code is `supabase/schema.sql` (tables, RLS policies, the `handle_new_user` signup trigger, and a
`pg_cron` schedule) and one Deno Edge Function, `supabase/functions/send-reminders`, invoked daily
by `pg_cron` to send weekly (Sunday) / month-end push reminders. `schema.sql` is idempotent and run
manually in the Supabase SQL editor — there are no migration files.

**Data layer (`src/lib/finance-data.ts`)** — every piece of server state (expenses, incomes,
categories, recurring expenses/incomes, budgets) is a TanStack Query hook in this one file,
including `useApplyRecurring`. Recurring expenses/income are not a separate "virtual" concept: this
hook materializes them into real `expenses`/`incomes` rows once per month (linked back via a
`recurring_expense_id`/`recurring_income_id` column), so afterward they're editable/deletable like
any manually-entered row. When adding a new data hook or mutation, this is the file to extend.

**Auth (`src/lib/auth.ts`)** — `useAuth()` wraps Supabase session state and sign in/up/out.

**Routing** — TanStack Router, file-based, under `src/routes/`. Only `/` exists today
(`src/routes/index.tsx`, `src/routes/__root.tsx` is the app shell). `routeTree.gen.ts` is
auto-generated — never hand-edit it. `src/routes/README.md` documents the file-based routing
conventions (e.g. don't create `src/pages/` or Next/Remix-style files) — read it before adding
routes.

**PWA / service worker** — `vite-plugin-pwa` runs in `injectManifest` mode (not the default
`generateSW`) specifically so `src/sw.ts` can add a custom Web Push handler; the manifest icons and
PWA metadata are configured in `vite.config.ts`, not a static `manifest.json`. `src/lib/push.ts`
holds the subscribe/unsubscribe helpers used from the UI.

**Budgets are monthly-only** — the Year view and "History → By year" intentionally omit
Planned/Remaining columns, since a budget is inherently a per-month concept. Don't add
year-level budget columns without checking this is actually wanted.

**Offline behavior** — the app is offline-*aware*, not offline-*capable*: `OfflineNotice.tsx` /
`use-online-status.ts` show a blocking "you're offline" screen rather than allowing degraded data
entry. There is no local write queue or offline cache of mutations.

## Conventions worth knowing

- Icon/favicon filenames in `public/` carry a `-v2` suffix (see comment in `index.html`) — bump the
  suffix on the next logo change so Safari's favicon cache (which ignores normal cache-busting)
  picks up the new file under a new URL, rather than reusing the same filename.
- `dist/` is the build output (gitignored, regenerated by `npm run build`); `netlify.toml` sets it
  as the publish directory and adds no-cache headers for `sw.js`/`manifest.webmanifest` specifically
  so Netlify's CDN doesn't add extra staleness on top of the browser's own service-worker re-check.
- Environment variables (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_VAPID_PUBLIC_KEY`)
  must be set in both `.env.local` (local dev) and Netlify site settings (deployed) — see
  README.md for where to get each one.
